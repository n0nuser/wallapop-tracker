# ADR 0003: Dashboard

Status: accepted

## Decision

A **single static `dashboard.html`** generated by a small stdlib script (`sqlite3` + a string template), opened directly in the browser. No server, no dependency. Datasette was prototyped and rejected.

## Context

The dashboard must filter listings by target, brand/model, compatibility, price, a target-specific derived metric, bargain-only, new-today and price-dropped, and show a price-history sparkline per listing and an "open on Wallapop" link. We prototyped both options against a fixture-built DB.

## Comparison

| | Datasette | Static HTML |
|---|---|---|
| Filters | one canned query per filter, ~50 lines of `metadata.json` | one `matches()` predicate, ~25 lines of JS |
| Are filters dynamic? | No — each filter is its own query; they do not combine | Yes — all filters combine live in the page |
| Numeric filters | form params arrive as strings; need `CAST(:p AS REAL)` | JS numbers, no coercion issue |
| Sparkline | needs a plugin or template | inline SVG, ~10 lines |
| Serving | a long-running server process | one file, opened or double-clicked |
| "Open on Wallapop" | free (Datasette links URLs) | free (an `<a href>`) |

## Why

- Datasette's canned queries are **one query per filter, not a filterable view**. Combining two filters means a new canned query per combination, or one query with many params — the thing the dashboard is *for* is the one thing Datasette does awkwardly.
- The sparkline is the blocker: a per-listing inline chart needs a Datasette plugin, i.e. real code plus a server to host it; in a static page it is a ten-line `<polyline>` over `observation.price_eur`.
- Matches ADR 0001 (stdlib + SQLite, simplest thing): nothing to install, patch or keep running.

## Revisit

- If the listing count grows large enough that re-rendering the whole table per keystroke is slow, move the filters into SQL — the `matches()` predicate already mirrors a `WHERE`, so it ports one-to-one.
- If the dashboard should be reachable off-LAN, any static host serves the file; that is a deploy decision, not a code change.

## Consequences

- The dashboard is generated by a script (`proto/make_dashboard.py`) from the SQLite DB; it reads targets and their specs from the DB, not from hardcoded product names.
- A `brand`/`model` filter is currently a title substring search: the extractor does not emit a brand/model field yet. Promote one when a filter needs it (per ADR 0002, a specs field becomes a column only when a filter needs it).
- The bargain flag is a placeholder inline in the prototype; the real rule is the scorer (`tracker/score.py`), and the prototype's `bargain()` is one function to swap.
